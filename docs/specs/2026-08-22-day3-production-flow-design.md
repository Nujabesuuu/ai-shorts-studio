# Day 3 — «Від демо до продакшну». Дизайн флоу та адмінки

Дата: 2026-08-22 · Статус: затверджено · Вертикаль: **спешелті-кав'ярня в Києві**

---

## 1. Задача і цільова функція

Згенерувати **реальний** контент вертикалі (не приклад роботи флоу), записати в Supabase,
показати в адмінці без ручних дій. Оптимізувати одночасно за трьома осями у пріоритеті
**якість : токени : швидкість = 2 : 1 : 1**.

| Вісь | Ціль | Доказ |
|---|---|---|
| Якість | максимальна | власна рубрика з 5 критеріїв; фінал не гірший за baseline **по кожному** критерію |
| Токени | мінімальні | сума токенів прогону; ціль **−30 %** від baseline |
| Час | мінімальний | end-to-end час прогону; порівняння baseline → фінал |

Схема доведення: baseline-прогін → фіксація токенів/часу по нодах → ≥2 ітерації
оптимізації → таблиця «до/після» з цифрами і поясненням змін.

Два дефекти попереднього прогону, які цей дизайн лікує явно:

1. **Інфляція оцінок.** `quality_score` = 100 / 100 / 91 / 100. Рубрика, яка всім ставить
   стелю, нічого не доводить.
2. **Розрив ніші.** `niche = "SaaS / IT-продукт"`, а `title` — «вторинне житло», «рекламний

Обидва стають вимірюваними критеріями рубрики (`uniqueness`, `traceability`).

## 4. Патерн декомпозиції та його обґрунтування

Обраний патерн: **конвеєр + ітерація + маршрутизація за умовою**.

Чому саме він, а не альтернативи:

- **Лінійний конвеєр «генератор → критик»** (мінімум по ТЗ) відкинуто: критик у кінці або
  нічого не змінює — і тоді нода декоративна, — або запускає регенерацію всього пакета, і
  тоді оптимізувати нічого, бо єдиний важіль — коротший промпт.
- **Супервайзер** відкинуто: додає LLM-ноду-диспетчер, яка щоразу платить токенами за
  рішення, що детерміністично обчислюється в `code` за 0 токенів.
- **Ітерація з умовним ремонтом** обрана, бо так робота тече насправді: одиниці контенту
  незалежні, а рішення «ремонтувати чи ні» ухвалюється **по кожній окремо**. Це дає і
  паралелізм (`parallel_nums: 10`), і структурний важіль економії — більшість одиниць
  проходить без третього виклику LLM.

## 5. Декомпозиція: агент → вхід → вихід → цінність

Кожна нода купує одну з трьох цінностей: **різні навички** / **незалежна перевірка** /
**швидкість (у т.ч. токени)**.

| # | Нода | Тип | Вхід | Вихід (типізовано) | Цінність |
|---|---|---|---|---|---|
| 1 | Start | `start` | `niche`, `platform`, `formats`, `n_items`, `flow_version` | — | вхідний контракт; `flow_version` мітить прогін для бенчмарку |
| 2 | Ніша → проєкт | `code` | `niche`, `project_id` | `project_filter`, `niche_norm`, `run_id`, `resolve_note` | швидкість: 0 токенів замість LLM-нормалізації |
| 3 | Get Rows · projects | `tool` | `project_filter` | `json: array[object]` | ідентичність проєкту |
| 4 | Get Rows · day2_topics | `tool` | `project_id` | `json` | первинне джерело брифів |
| 5 | Get Rows · day1_trends | `tool` | `project_id` | `json` | резервне джерело |
| 6 | Get Rows · day3_content | `tool` | `project_id` | `json` | антидубль → критерій `uniqueness` |
| 7 | Prepare briefs | `code` | 4×`json` | `briefs[]`, `count`, `source`, `notice` | швидкість: 3-гілкова маршрутизація джерела + дедуп детерміністично |
| 8 | Iteration · по брифах | `iteration` | `briefs[]` | `output: array[object]` | швидкість: незалежні одиниці, `parallel_nums: 10` |
| 8a | Compact brief | `template-transform` | `item` | `output: string` | токени: головний зріз input-контексту |
| 8b | **A1 · Продюсер** | `llm` | стиснутий бриф | **`structured_output: ContentDraft`** | навички: сценарій під формат і платформу |
| 8c | **A2 · Критик** | `llm` | `ContentDraft` + бриф | **`structured_output: QualityVerdict`** | незалежна перевірка за рубрикою з доказами |
| 8d | Потрібен ремонт? | `if-else` | `verdict` | `true` / `false` | швидкість: pass-одиниці не платять за 3-й виклик |
| 8e | **A3 · Ремонтник** | `llm` | `fix_list` + лише збиті поля | **`structured_output: ContentPatch`** | токени: патч замість регенерації |
| 8f | Apply patch | `code` | draft + patch | `result: object` | детерміністичне злиття, 0 токенів |
| 8g | Злиття гілок | `variable-aggregator` | 2 гілки | `output: object` | коректний єдиний вихід ітерації |
| 9 | Merge · score · rows | `code` | `iteration.output` | `rows_json`, `count`, `avg_score`, `by_criterion` | швидкість: зважений скоринг і валідація без LLM |
| 10 | Є що зберігати? | `if-else` | `count` | `true` / `false` | не будити агента даремно |
| 11 | Запис у day3_content | `http-request` | `rows_json` | `status_code`, `body` | bulk-insert у PostgREST: детерміністично, 0 токенів |
| 12 | Get Rows · перевірка | `tool` | `run_id` | `json` | незалежна перевірка факту запису |
| 13 | Перевірка запису | `code` | `json` | `saved`, `missing[]`, `report_md`, `tg_payload` | чесний звіт замість «агент сказав ок» |
| 14 | Telegram · звіт | `http-request` | `tg_payload` | `status_code` | доставка статусу людині |
| 15 | End · збережено | `end` | зведення | — | вихід |
| 16 | End · порожньо | `end` | `notice`, `resolve_note` | — | вихід порожньої гілки |

**Типізовані hand-off'и: 3** (мінімум за ТЗ — 2):

1. `A1 → A2`: `{{#A1.structured_output.*#}}`
2. `A2 → if-else → A3`: `{{#A2.structured_output.verdict#}}`, `.fix_list`
3. `A3 → Apply patch`: `{{#A3.structured_output.patch#}}`

Жодна нода не парсить стіну тексту — усі три переходи йдуть через `structured_output`
з JSON-схемою і `structured_output_enabled: true`.

## 6. Контракти hand-off'ів

### 6.1 `ContentDraft` (вихід A1)

```
format         string  enum: reels | carousel | stories
title          string  ≤ 90 символів, без емодзі
hook           string  дослівна перша фраза/дія 0–3 с
hook_alt       string  принципово інший захід, не перефразування
script         array   3–8 обʼєктів {n:number, t_start:number, t_end:number,
                       visual:string, voiceover:string}
onscreen_text  string  текст на екрані
caption        string  підпис під публікацією
hashtags       array   3–8 рядків з «#»
cta            string  заклик до дії
duration_sec   number  3–900
```

### 6.2 `QualityVerdict` (вихід A2)

```
scores   object  { traceability, production_ready, hook, format_fit, uniqueness }
                 кожен: { score: number 0–100, evidence: string }
verdict  string  enum: pass | repair | reject
fix_list array   { field: string, problem: string, instruction: string }
```

### 6.3 `ContentPatch` (вихід A3)

```
patch  object  лише ті ключі ContentDraft, що згадані у fix_list
note   string  що саме змінено
```

## 7. Рубрика якості

Ваги підібрані під цільову функцію: traceability і production_ready разом дають 50 %,
бо саме вони відрізняють «продакшн-реді» від «демо».

| Критерій | Вага | Що міряє | Правило проти інфляції |
|---|---|---|---|
| `traceability` | 25 | контент справді про свій тренд/тему; id прив'язаний | критик **цитує** фрагмент драфту як доказ; без цитати — стеля 60 |
| `production_ready` | 25 | знімається без додаткових питань: кадри з таймкодами, візуал, войсовер | відсутній таймкод у будь-якому кадрі — стеля 60 |
| `hook` | 20 | сила перших 0–3 с | загальна фраза без конкретики — стеля 55 |
| `format_fit` | 15 | відповідність формату і платформі | невідповідна кількість слайдів / тривалість — стеля 50 |
| `uniqueness` | 15 | не дублює `banned_titles[]` проєкту | збіг кута подачі — стеля 40 |

`quality_score = Σ(score × вага) / 100`, зважується **детерміністично в `code`-ноді**, а не
моделлю — модель дає лише покритерійні бали.

**Стеля 95.** Оцінка 96–100 дозволена лише коли `evidence` містить конкретну цитату;
інакше `code`-нода зрізає до 95. Це прямий фікс інфляції з §3.

Пороги статусу: `≥85 → ready`, `70–84 → needs_review`, `<70 → rejected`.
Поріг ремонту: `verdict = repair` при будь-якому критерії `<75`.

## 8. Протокол вимірювання

Оптимізація «на око» не зараховується, тому фіксуємо метод до першого прогону.

**Умови однаковості.** Один і той самий вхід для всіх конфігурацій: ніша
«спешелті-кав'ярня в Києві», `platform: instagram`, `formats: reels,carousel,stories`,
`n_items: 4`. Температура критика й ремонтника — `0`. Температура продюсера — `0.85`
(однакова в усіх конфігураціях, бо це параметр якості, а не оптимізації).

**Повторність.** По **3 прогони** на конфігурацію, у звіт іде **медіана**. Одиничний
прогін не є доказом: розкид токенів між прогонами Gemini на однаковому вході — одиниці
відсотків, і на дельті −30 % це шум, який треба відсікти.

**Джерело цифр.** Dify API, не око:

- `GET /v1/workflows/run/{workflow_run_id}` → `data.total_tokens`, `data.elapsed_time`
- по-нодно: node-executions → `execution_metadata.total_tokens`, `elapsed_time`

**Зберігання.** Таблиці `day3_runs` (агрегат по прогону) і `day3_run_nodes` (розклад по
нодах). Сторінка `/runs` в адмінці рахує дельти й показує, чи взято ціль −30 %.

**Критерій прийняття.** Фінал зараховується, якщо одночасно:
`tokens_final ≤ 0.7 × tokens_baseline` **і** `avg(criterion)_final ≥ avg(criterion)_baseline`
для **кожного** з 5 критеріїв.

## 9. План оптимізації

| Прогін | Що змінюємо | Механізм економії |
|---|---|---|
| **baseline** | чесна перша робоча версія: у промпт летить дамп **усіх** трендів і тем; A1 генерує і сам себе перевіряє; A2 критик **переписує обʼєкт цілком**; A3 — форматер, що ще раз проганяє готовий обʼєкт «на причесати»; 3 виклики LLM на кожну одиницю **завжди** | точка відліку |
| **iter 1** | `template-transform` стискає контекст до одного брифа; A2 віддає **лише** `scores` + `fix_list` замість переписаного обʼєкта | зріз input-токенів (контекст) і output-токенів (критик більше не генерує контент) |
| **iter 2** | скоринг, дедуп і валідація переїжджають у `code`-ноди; `if-else` пропускає A3 для `verdict = pass`; ноду-форматер видалено | зріз 3-го виклику для більшості одиниць + падіння latency |
| **final** | зріз дублювань у системних промптах, тюнінг `retry_config`, `max_tokens` для критика | добір до цілі |

Розширення наявної дизайн-системи «Broadcast Console», без переробки.

| Маршрут | Зміст |

**Автоматичність.** Адмінка читає ту саму таблицю, куди пише флоу. Нових рядків не треба
імпортувати руками — сторінки є Server Components і читають БД на кожен запит.

## 11. Ключі та безпека

- Telegram-токен і Dify-ключ живуть у `ai-shorts-admin/.env.local` (у `.gitignore`) і в
  `environment_variables` Dify. **У `.yml` секретів немає** — DSL посилається на
  `{{#env.TELEGRAM_BOT_TOKEN#}}`.
- Токен бота був переданий у відкритому чаті → після демо його треба відкликати через
  @BotFather (`/revoke`).
- RLS вимкнено на всіх таблицях: будь-хто з publishable-ключем читає й змінює всі рядки.
  Для воркшопу прийнятно, для продакшну — вмикати RLS **разом із політиками**.

## 12. Telegram

- **Нотифікації** (`http-request` у флоу): звіт про прогін — скільки одиниць, середній бал,
  скільки збережено, чого бракує.
- **Тригер** винесено **за межі Dify**: воркер у репо адмінки слухає `getUpdates` і смикає
  Dify API. Причина: `trigger-webhook` як вхідна нода прибирає ручний Run у Studio, а разом
  із ним — керований прогін для Tracing і чисте вимірювання токенів. Бот при цьому
  запускає флоу по-справжньому.

## 13. Межі (що свідомо не робимо)

- Не додаємо HITL у Day 3: гейт затвердження вже є в Day 2, дублювати його означає
  зупиняти конвеєр двічі за один ланцюг.
- Не генеруємо зображення/відео: ТЗ вимагає контент у БД і видимість в адмінці.
- Не вмикаємо RLS у межах цього завдання — це зламало б наявні Day 1 / Day 2 флоу.
